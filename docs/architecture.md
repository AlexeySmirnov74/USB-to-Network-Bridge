# USB to Network Bridge: architecture and implementation limits

USBBridge implements USB/IP 1.1.1. Device listing/import uses a short-lived management exchange; each imported device then owns a TCP connection. The data reader uses a one-second socket poll to observe cancellation and retries timeouts indefinitely, including mid-header reads. There is no session, trial or idle expiry. TCP keepalive detects a broken peer.

```text
Physical USB device
  -> unchanged production VBoxUSB driver
  -> Native Rust IOCTL/IOCP capture OR stock usbipd-win service
  -> configured TCP port (3240 by default)
  -> USBIP-WIN2 WSK client in the Windows kernel
  -> virtual USB device and normal Windows device-class driver
```

For direct connections the Rust client is a control application without an additional userspace copy in the client data path. It supports both the current development attach ABI and the published 0.9.8.1 ABI. A short-buffer rejection is the only condition that triggers the ABI fallback, before import has any effect.

Native opens VBoxUSB directly. usbipd-win is used to discover metadata, install the production drivers and reserve/release physical devices; its C# server does not forward Native session traffic. The signed SYS/CAT files remain unchanged. This is our own userspace capture implementation, **not a newly production-signed USBBridge kernel driver**.

Native uses pinned request storage, one IOCP worker per imported device, bounded completion queues and a byte budget. Transfer buffers remain alive until every asynchronous IOCTL completes. Isochronous requests are split at the VBoxUSB ABI limit of eight packets and 16-bit relative offsets, then compacted for USB/IP. TCP_NODELAY and pipelined requests avoid a userspace stop-and-wait loop.

Current limits that require hardware validation:

- VBoxUSB cancellation aborts an endpoint. Unlinking one request may also cancel other outstanding transfers on that endpoint.
- Isochronous transfers use the driver's ASAP scheduling. End-to-end frame clock synchronisation is not implemented.
- Zero-length-packet handling for bulk OUT with `URB_ZERO_PACKET` is rejected explicitly.
- USB hubs are not exported. Only selected devices are shared; a physical device has one active client.
- Task Scheduler starts the host/client recovery agents at boot under SYSTEM, without an execution time limit or battery restrictions. A separate per-user notification icon starts at logon. Driver installation remains a separate explicit operation.
- The unmodified client driver defaults to 30 USB 2 root ports and 30 USB 3 root ports. Removing licence counts does not remove USB address, controller or hardware limits.
- Windows x64 is the hardware-tested target. Synthetic protocol tests do not establish real-device support on other targets.

`src/usbdk.rs` preserves an optional earlier capture experiment. It is not installed by the production setup or included as a driver binary in release packages. The supported setup described in the README uses Native/VBoxUSB or the stock usbipd service.

A future USBBridge kernel capture module must go through its own Microsoft signing process before it can be offered for Secure Boot systems. Changing a signed upstream SYS invalidates its signature; another driver's production signature cannot be transferred to our binary. Relevant upstream material: [Microsoft driver signing](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/kernel-mode-code-signing-policy--windows-vista-and-later-), [USBIP-WIN2](https://github.com/vadimgrn/usbip-win2), [usbipd-win](https://github.com/dorssel/usbipd-win).

## Discovery, persistence and replug

UDP discovery sends nonce-bound queries on every active IPv4 subnet and accepts bounded replies from the sender's address. The host replies only to configured client IPs (or loopback), with a rate limit. Its persistent UUID distinguishes several servers and supports rediscovery after an address change; it is not an authentication key. Direct IP connections do not require discovery.

Client settings atomically persist successfully selected device identities. The recovery agent reconciles those identities with the live export list and kernel ports, with bounded exponential retry delays and no retry-count expiry. A failed management probe does not forcibly detach an existing connection. Driver reconnect attempts for a location are stopped before our agent starts another attach; other locations are untouched.

The native server monitors physical presence separately from transfer traffic. Two absent inventories close the stale session and release its exclusive lease. Cancellation polling is necessary because Windows did not reliably wake a blocking read when another socket clone was shut down. On replug, host maintenance reserves/shares only cached identities, using their current physical bus IDs. A location map updates Native's advertised bus IDs without restarting the server. Export selection and live sessions follow identities rather than old port numbers. Unknown replacement devices are not automatically selected.

Backend changes are serialised across manual use and the startup agent with a named mutex. State records desired and actual backends separately, plus PID, executable identity and creation time. Reservation rollback uses persistent GUIDs and instance identities, so it also handles offline or moved devices.

## Desktop, multiple servers and ports

The server window has a live inventory tab and a settings tab, with a large health indicator and a persisted start/stop control. Physical inventory comes from the installed usbipd-win `state` JSON. Native writes `native-sessions.local.json` only on import/release, recording bus ID and both TCP endpoints; there is no accounting in the transfer path. The desktop checks process identity and probes the actual listener before treating those sessions as live. A stopped or replaced process cannot leave a falsely connected row. Stock exposes client IP but no per-device client source port, so the UI does not invent one.

`Set-ServerState.ps1` changes the transport through UAC and pauses the owned recovery task during the operation. `HostSettings.enabled` defaults to true for older configs. A saved false value suppresses both export repair and automatic backend restart; the controller also stops an unexpectedly running backend while paused. Autostart and settings edits preserve the paused state. Restarting the server retains USB selections; client workers perform their usual recovery.

Before stopping stock, the backend helper persists the captured node and physical port for selected cached identities, requests their normal `usbipd detach`, and gives its workers a bounded interval to return the devices. If Windows still leaves a node pending removal (problem 21), it uses the existing targeted port recovery helper. The recovery verifies the device's current port; it does not restart an entire controller or enable administratively disabled devices. Pending releases remain in private backend state until handled.

The Win32 desktop uses a server/device tree with background discovery, inventory refresh and actions. The UI never forwards USB data. Several network addresses with one server UUID are grouped into one node; equal names with distinct UUIDs remain separate. Manual IP/hostname endpoints are supported. Discovery metadata is associated with an explicitly entered endpoint only when its advertised TCP port matches.

The selected server uses the original top-level settings fields; `servers` contains additional remembered connections. Switching the selection retains all saved device choices. Each connection has an independent reconciliation worker, so an unreachable server does not serialise recovery on the others. Attach rechecks the current selection under a device-specific operation lock; a concurrent disconnect cannot silently re-enable a saved target. Status reports include each server and use 64-bit Unix milliseconds for JSON compatibility.

Machine-wide named mutexes allow one client and one server application. UI, control and transport have separate lifetimes. A repeated GUI launch activates the existing window even when another config was supplied; repeated background controllers exit. Native also checks the stock server's documented-in-source singleton object, so separately launching it cannot start a second live module alongside usbipd-win. Synthetic protocol fixtures remain separate from physical-device server instances.

`Configure-Server.ps1` validates UI settings, applies server changes through UAC, updates scoped firewall ports and restarts the chosen backend/control task. TCP and UDP discovery ports are configurable. Stock uses the upstream `usbipd:Port` service argument; Native binds its configured endpoint directly. Failure attempts to restore the previous profile and host configuration. A TCP-port change can be rediscovered by UUID; changing the discovery UDP port requires configuring the client to search that port as well.

## Proxy transport and status catalog

Each saved server has an optional HTTP CONNECT, HTTPS CONNECT or SOCKS5 route. USBIP-WIN2 still connects through WSK; for a proxy route its destination is a per-server loopback listener owned by the Rust recovery worker. That listener negotiates the proxy and forwards both directions with bounded 256 KiB buffers and WSAPoll backpressure. Direct connections do not start a relay. Route state maps driver loopback endpoints back to the logical server and lets startup cleanup cancel only recorded stale reconnect attempts. Changing routes releases and recreates the affected attachments.

HTTPS uses Schannel with normal certificate/hostname verification and TLS 1.2 or newer. SOCKS5 resolves destination hostnames at the proxy. Configured credentials require authentication rather than permitting a silent downgrade; failed proxy connections never fall back to direct. Credentials are encrypted with machine-scope DPAPI, in files created with a protected SYSTEM/Administrators/Owner DACL, allowing the SYSTEM startup worker to read a GUI-saved credential. Configurations contain file paths only.

The host controller publishes a read-only JSON catalog over TCP on the configured discovery port. It includes physical identity, description, current USB port, publication, presence and client endpoint, including unpublished devices absent from USB/IP DEVLIST. The same peer-IP allowlist is enforced; connections have handshake timeouts, bounded message sizes and a concurrency limit. UDP discovery remains separate. Proxied clients use the proxy for both DEVLIST and this catalog; there is no remote mutation endpoint.

`Publish-Device.ps1` changes one explicitly selected identity through UAC, under the same local mutex as backend switching and USB recovery. It reads device/configuration descriptors through the parent Windows USB hub, without starting stock or stopping the Native transport. An atomic, validated publication snapshot supplies Native's live identity allowlist. Missing/malformed updates retain the last valid snapshot; an explicitly committed empty snapshot withdraws all exports. Adding or withdrawing another identity leaves existing sessions and the server process intact. Withdrawing an imported identity closes only its session before releasing its driver reservation. Driver activation may cycle only the selected, verified physical port when Windows defers that device's driver change. Stock uses per-device bind/unbind without restarting its service. Profile, cache and publication rollback never switch the whole backend. Changing backend or network settings still requires an explicit transport restart.

The descriptor cache preserves a stable logical slot for each identity, independently of its current physical port; a new identity reusing an old port receives a separate cache slot. Previously observed missing devices stay visible, with a disconnected state. Device ordering uses identity rather than port or publication status. A no-change GUI refresh does not rebuild controls; status changes update text in existing items, and structural updates preserve selection and viewport. Dependent fields, labels and conflicting actions are disabled according to the current form/operation state.

For Native live publication, a separate worker keeps a configured capture for each published device containing only HID interfaces (or device class HID). A boot mouse can advertise HID on its interface while its device class is zero; mixed camera/audio devices and hubs are excluded. The worker queues one read per interrupt IN endpoint of the default alternate setting. Idle report contents are discarded in memory without interpretation, forwarding or logging. Work and completion queues are bounded. An exclusive identity lease cancels and drains the idle reads before a client claims its own file and IOCP; idle capture resumes only after that session's file closes. DEVLIST and active transfers do not acquire the idle-worker lock. The worker retries after physical reconnection. On withdrawal, a process- and publication-revision-tagged acknowledgement lets `Publish-Device.ps1` wait for the idle capture and any imported session to close before restoring the local driver. A failed acknowledgement write releases idle captures. Force binding still removes the mouse from local use until publication is withdrawn.

Native's per-device `local_when_idle` option defaults off, preserving exclusive capture for existing camera configurations. Checked devices stay on their normal Windows driver while merely published. DEVLIST uses read-only Windows node presence for them, and IMPORT obtains an exclusive identity lease before invoking `Native-Capture.ps1` to reserve only the selected physical identity. The Rust IOCP transfer path is unchanged. Closing the last session queues restoration after its capture handle closes; restoration runs outside the session destructor to avoid deadlocking a publication helper that already owns the backend mutex. Nonblocking mutex acquisition retries busy releases. Ownership tokens prevent an older release from undoing a newer capture; the helper also checks the current Native PID/start time, publication and active sessions. Failed opens queue cleanup. Recovery does not force-bind opted-in devices, and switching/stopping Native releases their owned bindings. Unchecked HID devices retain the idle polling behavior above; opted-in HID devices use the local Windows HID driver instead. Changing the option during a session applies after that session closes. State retains identity-specific choices for unpublished devices and includes them in the atomic snapshot. The GUI exposes native row checkboxes and a checked context-menu action, reverting the visual toggle until saving succeeds. Column minima are measured using the actual header font and DPI.

## Development events

GUI, recovery controller, Native transport and PowerShell setup helpers write separate rotating JSONL logs beside the configuration. Events include user actions and selections, device identities/ports, session peers, retry transitions and operation errors. There is no payload/image logging in this channel. Credential/password/authorization/secret/token fields are redacted recursively; forms log labels and choice indices rather than free text. Each component keeps a 32 MiB current file and up to four rotated files. Logs remain private runtime data and are rejected by source packaging.

Both recovery controllers register Windows Configuration Manager notifications for USB/HID interface and device-instance arrival, enumeration, start and removal. Callbacks only copy bounded metadata into a 512-entry nonblocking queue. A worker records the event timestamp, normalized identity, interface class/path, driver service, parent identity, device status/problem and a separate state-sampling timestamp. Queue losses are counted explicitly. Notifications do not assert which process or firmware caused a reset; they provide timing to compare with driver operations and transport/session events. Startup on the server also records the cached devices' current Windows node states.

PowerShell helpers attach an operation UUID to each log line. Recovery snapshots record physical ports, forced-binding state and publication identities; driver commands log their arguments, process ID, exit status and duration. Native HID events record idle-capture acquisition, handoff, release and errors, without report contents. Concurrent script writers append complete lines using an exclusive writer with bounded retry. The common backend mutex is created with an explicit protected SYSTEM/Administrators ACL, so its access does not depend on which account starts first; opening an older object requests only synchronization/modify rights. Logging and mutex setup do not restart the transport.
